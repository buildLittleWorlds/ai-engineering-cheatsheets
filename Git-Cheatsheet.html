Start here · Two local source checkpoints

Preserve the starter. Preserve the checked improvement.

A complete beginner path for a small program that reads changeable material. Session 2 uses only this path: no branch, restore, remote, or answer-saving exercise is required. Run one command at a time at PS … >.

A · Check the boundary

Make sure Git belongs to this project

Open the new project folder in PowerShell. The PowerShell quick path shows how. First check:

git --version
git rev-parse --show-toplevel

“Not a git repository” is expected for a fresh folder outside an existing repository. After confirming the folder, run:

git init
git rev-parse --show-toplevel

The result must name this project folder. If the first check already names it, skip init. If either check names a larger parent folder, pause and get help before staging. init creates repository storage; it does not record a checkpoint.

B · Decide what belongs in history

Track the code; keep material separate

Create .gitignore in the editor and save these lines. This is file content, not a shell command:

reference.txt
private-notebook*
.env*
.venv/
__pycache__/
*.pyc

In this worked example, assistant.py is tracked, while reference.txt stays changeable and local. Keep a separate copy if you want to preserve particular material versions.

Ignore rules affect ordinary staging of untracked files. They do not erase previously tracked files, secure a secret, or prevent you from sending text to ChatGPT. Use non-sensitive material.

C · Checkpoint one

Save the working starter

Save and run the starter first. Then select just the two intended files and read what will enter history:

git add .gitignore assistant.py
git --no-pager diff --cached
git commit -m "Start with a manual AI harness"
git log -1 --oneline

add stages the current saved content. --cached shows that staged snapshot; --staged means the same thing. --no-pager keeps the output directly in the terminal. Commit only after reviewing it; the final line verifies a recorded checkpoint.

Nothing is uploaded. No GitHub account is needed. If files beyond the intended source appear, stop and check the folder and staging selection.

D · Checkpoint two

Save the capability you checked

After adding file reading, inspect the printed packet and the response. Change the reference detail, save, and rerun with the same question. Then review and preserve the source:

git --no-pager diff -- assistant.py
git add assistant.py
git --no-pager diff --cached -- assistant.py
git commit -m "Let my harness use reference material"
git log --oneline -2
git status --short

Point to the added file read and prompt text. The log should show both checkpoints. No output from status can coexist with changes to ignored reference.txt: those material changes remain on disk but are not preserved by these commits.

E · Setup support

If Git asks who you are

Privately check the configured identity:

git config --get user.name
git config --get user.email

If missing or someone else’s, choose your own values. Replace both placeholders before running:

git config --local user.name "YOUR CHOSEN DISPLAY NAME"
git config --local user.email "YOUR CHOSEN EMAIL"

This changes only the current repository’s configuration. Identity becomes part of commits; do not submit those values as evidence. If setup or device policy blocks Git, keep building and record the exact blocker rather than disabling protections.

F · Explain the checkpoint

A commit is a record, not a quality claim

Keep the three saves distinct: Ctrl+S saves an editor file; git add chooses content; git commit records it in history. A commit does not include the model’s answer or ignored material just because they were part of the same experiment.

Record a safe reference detail → its text in the packet → the observed response, plus the source version you kept or the checkpoint blocker. Python reads the file; the model sees only the packet you send.

For Session 2’s single progress note, report progress, evidence, one decision and limitation, and one next step. Label actual/manual, simulated, observed, failed, and unfinished work accurately. A useful investigated failure counts; a simulated answer is not evidence of model use.

Next · Ten everyday workflows in more detail

Build your Git vocabulary as you need it

The quick path above is sufficient for two checkpoints. The reference below adds more ways to inspect and select work, then optional branching, undo, temporary storage, and collaboration.

Start here · Read only

01See where you stand

git status
git status --short --branch

See your branch and which files are staged, modified, or untracked. The second command gives a compact view.

Read the labels: “Changes to be committed” are staged. “Changes not staged” need review. “Untracked” files have not been added. A clean working tree means no pending tracked-file changes and no reported untracked files; ignored files can still differ. It does not mean you pushed.

Review · Read only

02Inspect what changed

git diff
git diff --staged
git diff -- assistant.py

git diff compares unstaged tracked-file edits with the staging area. --staged compares the staged snapshot with your latest commit. The last line reviews one file.

Habit: review both before committing. Untracked files do not appear in ordinary git diff; open them yourself or stage them and review the staged diff. Use git --no-pager diff to avoid a pager, or press q to exit one.

Choose your next snapshot

03Stage selected changes

git add -- assistant.py
git add -- README.md
git diff --staged

Stage the files you intend to save, then inspect that snapshot. git add records the file as it looks now; if you edit it again, add it again to include those edits.

Outside the guided example: git add -A stages all additions, modifications, and deletions across the repository. Review first; the guided path deliberately selects named files instead. Keep keys, .env, and generated output out of commits.

Save a local checkpoint

04Commit a working step

git diff --staged
git commit -m "Read reference material in the prompt"
git status

Run your program or relevant checks first. Commit the staged changes with a message that says what changed. Your checkpoint stays on this computer until you push or back up the repository.

Remember: a commit includes staged content. Unstaged edits and untracked files stay outside that checkpoint. “Nothing to commit” usually means nothing is staged or nothing changed.

Find a checkpoint · Read only

05Read your saved history

git log --oneline -10
git log --oneline --graph --all
git show HEAD

Find recent commit IDs and messages, see the branch history as a small text graph, and inspect the latest commit. Press q if Git opens a pager.

To inspect a particular checkpoint, copy its ID from the log and use git show COMMIT_ID, replacing COMMIT_ID with that actual ID. Viewing history does not change your files.

Optional next level · Not needed for two checkpoints

06Create and switch branches

git branch --show-current
git switch -c experiment
git switch main

Note your starting branch. Create and enter a new experiment branch, do your work, then return to your starting branch (shown as main). If the branch already exists, use git switch experiment.

Before switching: commit or stash unfinished edits. Otherwise they may follow you, or Git may block the switch. Commits stay on the branch where you made them. Untracked and ignored files can remain when you switch.

Keep a successful experiment

07Bring a branch back together

git switch main
git merge experiment
git status

First commit the finished experiment and start clean. Switch to the branch that should receive the work, then merge the experiment into it. Test the result. Git may move the branch forward or create a merge commit; if an editor opens, save its message and close it.

If there is a conflict: run git status, open the listed files, choose the intended content, and remove conflict markers. Test, git add -- FILE for each resolved file, then git commit. To cancel an in-progress merge, use git merge --abort. Ask for help if you cannot explain which content to keep.

Choose the right kind of undo

08Unstage, restore, or revert

Unstage a file; keep your edits:

git restore --staged -- assistant.py

Use after the first commit. Before that first commit, git rm --cached -- assistant.py unstages a newly added file while keeping the working file.

Discard only unstaged edits to this tracked file:

git diff -- assistant.py
git restore -- assistant.py

Restore replaces the working file with its staged version. Discarded edits may be unrecoverable. To recover an older version, use git restore --source=COMMIT_ID -- assistant.py with an actual ID, after saving any current edits you need.

Undo a saved, ordinary commit with a new commit:

git revert --no-edit COMMIT_ID

Replace the ID and start clean. This preserves history. If conflicts occur, resolve and stage the files, then git revert --continue, or cancel with git revert --abort. Merge commits need a different procedure.

Pause unfinished work

09Set edits aside and resume

git stash push -u -m "Pause prompt-formatting work"
git stash list

Temporarily save tracked-file edits and untracked files with -u. Ignored files stay in place. This requires an existing commit. Do the other task, then return to the original branch before restoring:

git stash apply

apply restores the latest stash and keeps the saved stash as a backup. Review with git status, resolve conflicts if any, then stage and commit when ready. After verifying the latest stash is no longer needed, git stash drop removes it.

Optional · Shared remote repository

10Download and upload commits

git remote -v
git branch -vv
git pull --ff-only
git push

Inspect remote addresses and your branch’s upstream, then download updates and upload commits. Use with a configured remote and upstream, appropriate access, and a clean working tree. Review the remote address and committed history before sharing.

pull --ff-only updates only when your branch can move straight forward. If histories diverged, stop and inspect instead of forcing. A rejected push can mean the remote has newer commits; coordinate and integrate them first.

For a new local branch, git push -u origin experiment uploads it and sets its upstream. Replace the names as needed. This creates a remote branch and shares committed content with people who have access.

Other projects · Alternatives and deeper inspection

Start another project or investigate tracking

git --version checks that Git is installed. Use PowerShell’s cd to enter your project folder. Check git rev-parse --show-toplevel before initializing. These are alternatives for another project; do not reinitialize the worked example.

Start tracking an existing local folder

git init -b main
git config user.name "Your Name"
git config user.email "you@example.com"

Run inside the intended project, not its parent or an existing repository. Replace the name and email with your own; these commands set identity for this repository. The identity becomes part of commits.

Copy an existing remote project

git clone REPOSITORY_URL project-copy
cd project-copy

Replace REPOSITORY_URL with the actual clone URL and choose a new destination folder. Clone brings history, checks out a branch, and normally configures origin and an upstream. Set your commit identity here too if needed.

Other projects: choose ignore rules deliberately

Create .gitignore in the project. A Python project might start with these patterns (file contents, not terminal commands):

.env
.venv/
__pycache__/
*.pyc

Add your project’s exact generated-output paths if those should stay local, then stage and commit .gitignore. Ignore rules do not stop tracking files already committed, and removing a secret from today’s file does not remove it from old commits.

Why is a file missing from status?

git check-ignore -v -- reference.txt
git ls-files -- reference.txt
git status --short --ignored

The first command identifies an applicable ignore rule for an untracked file. The second lists the file if Git already tracks it. The last includes ignored items, marked !!. An ignored file still exists on disk; it is not a saved version. Do not force-add material simply to make it appear.

Your daily loop: git status → edit and test → git diff → git add -- FILE → git diff --staged → git commit -m "What changed" → git status. Repeat for each small, understandable step.
